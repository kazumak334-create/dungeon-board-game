# DeckPrep UX改善企画書

作成日: 2026-04-10
優先度: 高（Phase 3重点タスク）

---

## 概要

DeckPrep画面の使いやすさを向上させるための3項目の改善提案。
初見プレイヤーが「どこに何を置くべきか」を直感的に理解できるよう、視覚的フィードバックを強化する。

### 改善項目

1. **盤面マスのドロップヒント**（最優先）
2. **手持ちカードの分離表示**（中優先）
3. **呪文デッキの存在感強化**（低優先・バランス調整時に検討）

---

## 改善項目1: 盤面マスのドロップヒント（最優先）

### 目的

初見プレイヤーが「前列と後列の違い」を理解する最大の障壁を解消。
「どこに置くと何になるか」が一目で分かるようにする。

### ユーザー体験への影響

**現状の問題**:
- 前列＝攻撃、後列＝サポートという概念を理解していないと配置を誤る
- ドラッグ中にドロップ可能なマスが分からない
- 配信視聴者も「どこに置けるか」が分からない

**改善後**:
- ドラッグ開始と同時に配置可能なマスが光る
- 前列マスに攻撃アイコン、後列マスに盾アイコンが表示される
- 「ここに置くとアタッカーになる」「ここに置くとサポートになる」が視覚的に伝わる

### ビジュアルデザイン

#### ドラッグ中の表示

**配置可能なマスの背景**:
- 色: `Color(0.9, 0.75, 0.3, 0.3)` — 金色（半透明）
- アニメーション: 0.2秒でフェードイン（Tween・EASE_OUT）
- ドラッグ終了時: 0.15秒でフェードアウト（Tween・EASE_IN）

**アイコン表示**:

| 列 | アイコン | 位置 | サイズ | 色 |
|----|---------|------|--------|-----|
| 前列（col=2） | ⚔️ 攻撃 | マス中央 | 32×32px | `Color(0.9, 0.35, 0.35)` 赤系 |
| 中列（col=1） | ⚔️/🛡️ 両方 | 上下2段 | 各24×24px | 赤系・青系 |
| 後列（col=0） | 🛡️ 盾 | マス中央 | 32×32px | `Color(0.5, 0.7, 0.9)` 青系 |

**アイコン実装方針**:
- アイコンは簡素な図形で表現（三角形＝攻撃、円形＝盾）
- テクスチャ不要、Polygonで描画
- ホバー時は常に表示、ドラッグ終了時に非表示

#### 配置不可マスの表示

- 色: `Color(0.2, 0.15, 0.15, 0.5)` — 暗い赤系（半透明）
- アイコン: ❌ マーク（中央、サイズ28×28px、`Color(0.6, 0.2, 0.2)`）

### UI基準との整合性

| 基準 | 評価 | 理由 |
|-----|------|------|
| 3秒ルール | ✅ | ドラッグ開始と同時に配置可能マスが光る。アイコンで役割が即座に伝わる |
| 視線の一本化 | ✅ | 盤面マス上に直接表示。視線移動なし |
| 状態の可視化 | ✅ | 配置可能/不可を色とアイコンで明示 |
| 操作の最小化 | ✅ | 操作そのものは変更なし。視覚的フィードバックのみ追加 |
| 配信映え | ✅ | ドラッグ操作が視聴者にも一目で伝わる |
| 世界観の匂わせ | ⚠️ | アイコンは無機質なデザインを維持（三角形・円形の図形表現） |

### 実装方針

**変更ファイル**: `scripts/DeckPrepBoard.gd`

**新規メソッド**:
- `_show_drop_hints(dragged_card_type: String) -> void` — ドロップヒント表示
  - ドラッグ開始時に呼び出し
  - カード種別（ユニット/呪文）に応じて配置可能マスを判定
  - 背景色変更 + アイコン表示（Polygon）
- `_hide_drop_hints() -> void` — ドロップヒント非表示
  - ドラッグ終了時に呼び出し
  - 背景色をデフォルトに戻し、アイコンを削除

**既存メソッドへの接続**:
- `start_drag_group()` — ドラッグ開始時に `_show_drop_hints()` 呼び出し
- `end_drag()` — ドラッグ終了時に `_hide_drop_hints()` 呼び出し

## 改善項目2: 手持ちカードの分離表示（中優先）

### 目的

ユニットカードと呪文カードを視覚的に分離し、「どこにドラッグすべきか」の迷いをなくす。

### ユーザー体験への影響

**現状の問題**:
- 手持ちカードが混在表示（ユニット・呪文が区別されていない）
- 呪文を盤面にドラッグしようとして失敗する
- ユニットを呪文デッキにドラッグしようとして失敗する

**改善後**:
- ユニットカード: 左側エリア（盤面に近い位置）
- 呪文カード: 右側エリア（呪文デッキに近い位置）
- ラベル色でも区別（ユニット＝緑系、呪文＝青系）

### ビジュアルデザイン

#### レイアウト

| エリア | 位置 | サイズ | 表示内容 |
|--------|------|--------|---------|
| ユニットカードエリア | (210, 580) | 430×80 | ユニットカードのみ |
| 呪文カードエリア | (645, 580) | 425×80 | 呪文カードのみ |

#### ラベル

| エリア | テキスト | フォントサイズ | 色 |
|--------|---------|--------------|-----|
| ユニットカード | 「ユニット」 | 11 | `Color(0.6, 0.7, 0.6)` 緑系 |
| 呪文カード | 「呪文」 | 11 | `Color(0.6, 0.65, 0.85)` 青系 |

#### 背景

- ユニットエリア: `Color(0.12, 0.14, 0.13)` — 緑がかった背景
- 呪文エリア: `Color(0.12, 0.13, 0.16)` — 青がかった背景

### UI基準との整合性

| 基準 | 評価 | 理由 |
|-----|------|------|
| 3秒ルール | ✅ | ユニット・呪文の区別が即座に分かる |
| 視線の一本化 | ✅ | 左側（ユニット）→ 盤面、右側（呪文）→ 呪文デッキの視線の流れ |
| 状態の可視化 | ✅ | カード種別が色とラベルで明示 |
| 操作の最小化 | ✅ | ドラッグ距離が短縮される |
| 配信映え | ✅ | 配信視聴者にも「どこに何をドラッグするか」が伝わる |
| 世界観の匂わせ | ✅ | MaterialSelect.gdの色彩設計を踏襲 |

### 実装方針

**変更ファイル**: `scripts/DeckPrepBoard.gd`

**変更メソッド**:
- `_build_spell_artifact_split()` — 手持ちカード描画ロジック
  - 既存の `_build_hand_card_container()` を2つに分割
  - `_build_unit_card_container()` — ユニットカードのみ表示
  - `_build_spell_card_container()` — 呪文カードのみ表示
  - カード種別フィルター: `CardDB.UNITS.has(card_name)` / `CardDB.SPELLS.has(card_name)`

## 改善項目3: 呪文デッキの存在感強化（低優先）

### 目的

呪文デッキが「ここに呪文をドラッグする」という重要なエリアであることを明示する。

### ユーザー体験への影響

**現状の問題**:
- 呪文デッキが右端の小エリアに配置されており、存在感が薄い
- 初見プレイヤーが「呪文デッキにドラッグする」という操作に気づかない

**改善後**:
- 呪文デッキエリアを盤面と同等の視覚的重要性を持たせる
- 背景・枠線を強調して「ここに呪文をドラッグする」と直感的に分かる

### ビジュアルデザイン（案）

#### 案A: 呪文デッキを中央コンテンツ下部に移動

| エリア | 位置 | サイズ | 説明 |
|--------|------|--------|------|
| 盤面グリッド | (210, 80) | 360×360 | 現行通り |
| 呪文デッキ | (580, 80) | 490×360 | 右側に大きく表示 |
| 手持ちカード | (210, 450) | 860×130 | 下部に横長表示 |

#### 案B: 呪文デッキを盤面右側に縦長表示

| エリア | 位置 | サイズ | 説明 |
|--------|------|--------|------|
| 盤面グリッド | (210, 80) | 360×360 | 現行通り |
| 呪文デッキ | (580, 80) | 200×360 | 縦長カード表示 |
| 手持ちカード | (210, 450) | 860×130 | 下部に横長表示 |

### UI基準との整合性

| 基準 | 評価 | 理由 |
|-----|------|------|
| 3秒ルール | ✅ | 呪文デッキの存在が一目で分かる |
| 視線の一本化 | ⚠️ | 案A・Bともに視線の流れが複雑化する可能性 |
| 状態の可視化 | ✅ | 呪文デッキが常に可視化 |
| 操作の最小化 | ✅ | ドラッグ距離が短縮される |
| 配信映え | ✅ | 呪文デッキの存在が配信視聴者にも伝わる |
| 世界観の匂わせ | ✅ | 色彩設計は変更なし |

### 重要な設計判断

**慎重に検討すべき理由**:
- DeckPrep画面の核となる体験は「盤面を設計する」こと
- 呪文デッキの存在感を強化しすぎると、盤面設計の重要性が相対的に低下する
- 現状の配置（右端の小エリア）は「補助的な要素」という位置づけを明示している

**推奨方針**:
- 項目1・2の実装完了後、ユーザーテストで「呪文デッキにドラッグする」操作の成功率を測定
- 成功率が低い場合のみ、存在感強化を検討
- まずは項目2（手持ちカード分離表示）で「呪文カードを右側に配置」することで改善できるか確認

## 実装優先度と段階的導入

### Phase 1: 最優先実装（項目1）

**対象**: 盤面マスのドロップヒント

**理由**:
- 初見プレイヤーの最大の障壁（前列/後列の違い）を解消
- UI基準の「3秒ルール」に最も貢献
- 実装コストが低い（既存のドラッグ&ドロップロジックに接続するだけ）

**実装期間**: 2-3時間

### Phase 2: 中優先実装（項目2）

**対象**: 手持ちカードの分離表示

**理由**:
- ドラッグ操作の認知負荷削減
- 配信映えに貢献
- 実装コストは中程度（手持ちカード描画ロジックの分割が必要）

**実装期間**: 3-4時間

### Phase 3: 低優先検討（項目3）

**対象**: 呪文デッキの存在感強化

**理由**:
- Phase 1・2の効果測定後に判断
- 盤面設計の核となる体験を損なう可能性
- 実装コストは高い（レイアウト全体の再設計が必要）

**実装期間**: Phase 1・2の効果測定後に決定

## 制約と非変更領域

### 変更しない箇所（厳守）

- デッキ管理ロジック（GameSession.selected_deck）
- placement_config（配置情報の保存形式）
- カード種別判定ロジック（CardDB.UNITS / CardDB.SPELLS）
- ドラッグ&ドロップの既存ロジック（start_drag_group / try_drop_card）

### 変更範囲

- UI描画（ColorRect / Label / Polygon等のノード生成）
- 視覚的フィードバック（Tween / modulate変更）
- レイアウト調整（position / size変更）

## まとめ

DeckPrep画面の使いやすさを向上させるための3項目の改善提案を整理した。

**最優先**: 盤面マスのドロップヒント（初見プレイヤーの障壁解消）
**中優先**: 手持ちカードの分離表示（ドラッグ操作の認知負荷削減）
**低優先**: 呪文デッキの存在感強化（Phase 1・2の効果測定後に判断）

段階的実装により、リスクを最小化しながらUXを向上させる。
