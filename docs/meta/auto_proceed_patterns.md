# 自律進行パターン定義

更新日: 2026-04-29

Claudeが「ユーザーの承認なしに自律的に進めてよい状況」と「必ず止まって確認すべき状況」を定義する。
セッション開始時およびタスク着手前に参照すること。

---

## 承認不要パターン（Auto-proceed）

以下のいずれかに完全に該当する場合、ユーザー承認なしに実装を進めてよい。

### 1. バグ修正

条件:
- 症状が明確にコードの誤りに対応している
- 設計変更・仕様変更を伴わない
- 変更ファイルが3ファイル未満

例:
- `is_alive = false` 後に `visible = false` が漏れていた
- null チェックなしで関数を呼んでいたためクラッシュしていた

### 2. プロセスタスク

条件:
- 実装内容ではなく、管理・記録・検証の作業である

対象:
- `roadmap.md` / `CHANGELOG.md` の更新
- `check_syntax.sh` / `checker.md` の更新（エラー学習）
- 構文チェック（`check_syntax.sh`）の実行

### 3. 要件定義書の同期更新

条件:
- 新しい要件の追加ではなく「実装の現状に合わせる」同期である
- 既に動いている実装と要件定義書の記述が乖離している

例:
- マップ列数が実装=11列だが要件書=6列のまま
- 関数名がリファクタリングされたが要件書に古い名前が残っている

### 4. 将来計画セクションへの追記

条件:
- 現Phaseの未着手スプリント（Sprint N）への追加である
- 既存の実装に触れない純粋な文書追記である

対象:
- req doc の「将来実装機能」セクションへの追記
- `roadmap.md` の未着手タスク列への追加

### 5. エラー学習の記録

条件:
- エラーを修正した直後の後処理である

対象:
- `checker.md` への新パターン追記
- `check_syntax.sh` への grep ルール追加

## 必ず止まって確認するパターン（Must-stop）

以下のいずれかに該当する場合、実装を止めてユーザーに報告し承認を得ること。

報告フォーマット:
```
⚠️ 確認が必要です

該当パターン: [パターン番号・名称]
指示内容: [何をしようとしているか]
理由: [なぜ確認が必要か]
確認: 進めてよいですか？
```

### 1. 新機能追加

トリガー:
- 指示されていない機能・要素を追加しようとしている
- 「ついでに」追加しようとしている

例:
- ハーベスターへの小麦採掘機能追加（指示なし）
- 既存カードへの新しいスキル付与

### 2. ゲームバランス変更

トリガー:
- ユニットの数値パラメータを変更しようとしている

対象パラメータ:
- `spd` / `atk` / `hp` / `move_spd`
- BUILD_COSTS / カードコスト
- マナ生成量・回復量

例:
- Attacker の spd 1.5→1.0 への変更
- Village のコスト変更

### 3. UI/UX の再設計

トリガー:
- 既存UIコンポーネントの削除または置き換えを行おうとしている
- 画面レイアウトを変更しようとしている

例:
- スライダーを線分バーに変更
- パネルの配置変更

### 4. 要件定義書への新規仕様追加

トリガー:
- 既存コードにない新しい要件を要件定義書に追加する
- 設計方針・制約の変更を要件定義書に書き込む

例:
- WHEAT タイル仕様の新規定義
- 農村隣接制約の追加

### 5. 廃止済み設計に触れる変更

トリガー:
- `CLAUDE.md` の廃止リストに記載されたシステムに関連する変更

廃止リスト（抜粋）:
- 盤面召喚システム
- 時間経過マナ回復
- アクティブスキル・固有スキル
- 本体HPシステム

### 6. 複数ファイルにまたがる設計変更

トリガー:
- 3ファイル以上を変更するアーキテクチャ変更
- シグナル構造・クラス継承関係の変更

例:
- CombatSystem + EnemyAI + GameUI を同時リファクタリング

---

## 判定フロー

タスクを受け取ったとき:

1. 「承認不要パターン」の全条件を確認する
2. 全条件を満たす → そのまま進める
3. 1つでも条件を外れる → 「必ず止まって確認するパターン」を確認する
4. 該当パターンがある → 報告フォーマットで確認する
5. どちらにも明確に当てはまらない → 確認する（不明確な場合は止まる）
