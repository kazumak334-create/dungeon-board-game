# UI/UX実装ワークフロー

作成日: 2026-04-10

UI/UX実装の正しい業務フローを定義する。

---

## ワークフロー全体像

```
1. Designer Agent: UI/UX企画作成
   ↓
2. CEO: 企画承認
   ↓
3. ui Agent: 企画に基づいて実装
   ↓
4. checker Agent: 企画通りか検査
   ↓
   NG → ui Agentに差し戻し（手順3に戻る）
   OK → コミット
```

---

## Phase 1: UI/UX企画（Designer Agent）

### 責務
画面のUI/UX設計・レイアウト企画・デザイン仕様策定

### 成果物
以下を含む企画書（Markdown形式）:

1. **画面の目的**
   - この画面で何を達成するか
   - ユーザーが何を判断・選択するか

2. **レイアウト構成**
   - 画面を領域分割（ヘッダー・メイン・サイドバー・フッター等）
   - 各領域のサイズ・配置（座標・幅・高さ）
   - 視線の流れ（上→下、左→右など）

3. **色彩設計**
   - 背景色・パネル色・強調色の定義
   - 既存画面（MaterialSelect.gd等）との統一感
   - 色定義の定数名（COLOR_BG, COLOR_PANEL等）

4. **UIコンポーネント一覧**
   - ボタン・ラベル・パネル・スクロール等の配置
   - 各コンポーネントのサイズ・位置・テキスト

5. **インタラクション**
   - クリック・ホバー・ドラッグ等の操作
   - 状態変化（購入済み・選択中等）の表現方法

6. **UI基準チェック**
   - 3秒ルール: 3秒で何ができるか分かるか
   - 視線の一本化: 複数の注意点がないか
   - 状態の可視化: 現在の状態が一目で分かるか
   - 操作の最小化: クリック数は最小か
   - 配信映え: 視聴者に伝わるか
   - 世界観の匂わせ: ダークファンタジー+無機質な整合性

### 完了条件
- 企画書が上記6項目を満たしている
- CEOが承認した

---

## Phase 2: 実装（ui Agent）

### 責務
承認された企画書に基づいてGDScriptで実装

### 入力
- Phase 1で作成された企画書
- 既存の参考ファイル（MaterialSelect.gd等）

### 成果物
- 実装済みGDScriptファイル（.gd）

### 完了条件
- 企画書の全項目を実装した
- 構文エラーなし
- 既存画面との統一感がある

### やってはいけないこと
- 企画書にない機能・レイアウトの追加
- 色定義・サイズの勝手な変更
- ハードコード

---

## Phase 3: 検査（checker Agent）

### 責務
企画書通りに実装されているか検証

### チェック項目

1. **企画書との整合性**
   - レイアウト構成は企画通りか
   - 色定義は企画通りか
   - UIコンポーネントは全て実装されているか
   - インタラクションは企画通りか

2. **コード品質**
   - ハードコードがないか
   - 定数化されているか
   - 既存コードとの統一感があるか

3. **動作確認**
   - 構文エラーがないか
   - テストが全パスしているか（該当する場合）

### 完了条件
- 全チェック項目をパスした

### NG時の対応
- 差し戻し理由を明確に記載
- ui Agentに修正を依頼（Phase 2に戻る）

---

## Phase 4: コミット（CEO）

### 条件
- checker Agentが合格を出した
- 実装内容を最終確認した

### 実施内容
- git commit
- CHANGELOG.md更新（必要に応じて）
- roadmap.md更新（タスク完了マーク）

---

## 注意事項

### CEOの役割
- **企画承認のみ**。実装には関与しない
- 企画が不十分な場合はplanning Agentに差し戻し
- 実装がおかしい場合はchecker Agentの検査を信頼

### Agent間の引き継ぎ
- planning → ui: 企画書（Markdown）を渡す
- ui → checker: 実装ファイルパスと企画書を渡す
- checker → CEO: 検査結果（合格/不合格+理由）を渡す

### 企画書の保存場所
- `docs/design/ui/[画面名].md`
- 例: `docs/design/ui/shop.md`

---

## 企画修正プロセス

### 修正トリガー（いつ修正するか）

1. **実装前の差し戻し（CEOによる企画承認時）**
   - 企画が不十分（レイアウト未定義、色彩設計なし等）
   - UI基準6項目が未チェック
   - GAME_DESIGN.mdと矛盾

2. **実装後の差し戻し（実装済みコードとの乖離発見時）**
   - 既に実装済みのコードと企画が食い違っている
   - 廃止済み機能が企画に含まれている
   - 実装が不可能な仕様が含まれている

### 修正者（誰が修正するか）

- **planning Agent**が修正を担当
- CEOは修正指示のみ行い、自ら修正しない

### 修正基準（何を基準にするか）

優先順位（上が優先）：
1. GAME_DESIGN.md（設計文書）
2. 実装済みコード（.gdファイル）
3. CLAUDE.md（開発ルール）
4. UI基準6項目（3秒ルール、視線の一本化等）

### 確認者（誰が確認するか）

- **CEO**が修正結果を確認
- 修正が不十分な場合は再度差し戻し
- 最大3回まで差し戻し可能、3回目で不合格の場合はCEOが手動修正

### 差し戻しフォーマット

planning Agentへの差し戻しプロンプトには以下を含める：

1. **差し戻し理由**（何が問題か）
2. **修正基準**（何を参照すべきか）
3. **修正箇所**（どこを直すか）
4. **正しい仕様**（正解は何か）
5. **確認方法**（どうやって検証するか）
